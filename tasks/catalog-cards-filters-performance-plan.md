Preserve one card per row below 600 CSS px and four at desktop widths of 1024 CSS px and above.
- Replace the card's Share text and outlined pill with a plain share icon, retaining a minimum 44×44 px target, an accessible name such as “Share InsaneCraft Pack 1.6”, focus indication and the existing native chooser, thumbnail preparation and copy fallback. Do not remove detail-page sharing unless separately requested.
- Remove “How it works” beside the hero button; relabel that button “Browse DLCs”. Remove the visible collection eyebrow, heading, explanatory copy, count and category chips, including redundant visible hero category shortcuts if they otherwise recreate the removed list. Keep a visually hidden heading so the catalog section remains identifiable to screen readers; keep meaningful non-category content in the desktop hero.
- Add professional icons for Auto/Light/Dark. Plan a compact, keyboard-operable theme control with clear selected state and accessible names, keeping the preference and OS-following behavior and reduced-motion support. Avoid arrows/emojis, gradients or glow. Maintain the user's #c88828 accent and supplied branding.

## 2. Search and filters

- Keep the search field and its existing debounced catalog suggestions, but put a search icon inside the field and a separate, icon-only file/filter button on its right. Both controls need accessible labels and at least 44 px targets; Enter must still search. An accessible popover/drawer opens from the button, with Escape/outside dismissal, return focus, explicit Apply and Clear, and a visible indicator when filters are active.
- Move category choices into that panel. Provide All plus the existing categories; preserve legacy `?cat=` links, home/search routes, search text, pagination, back navigation and `?i=1` host behavior. Represent filters in validated, shareable query parameters, not only in UI state. Combine search, creator, category and date filtering on the server before pagination; client-side filtering of just 24 results would miss catalog items.
- Date caveat: the current Worker has only `updated_at`, sourced from the bot record's `updatedAt`; this can change on re-upload/update and is not a proven original upload date. Do not call it upload date. Ask whether to provide a clearly labeled “Last updated” filter first, or wait for a trustworthy upload timestamp. A genuine upload-date filter would require confirming a durable source, source semantics, pipeline changes and potentially a separately approved D1 migration/backfill. Do not apply the 12 pending Telegram database changes.
- Existing Worker allows category and free-text query but not exact creator or date filtering. Extend the public read endpoint only as needed, with strict parameters and bound SQL; preserve default behavior, CORS, `CATALOG`, `SYNC_SECRET`, UUID links and `Cache-Control: no-store`. Review performance/index need on realistic data; any D1 schema/index change and Worker deployment is separately documented and gated, with rollback.

## 3. Pack details and studio links

- Show labeled fields per actual item: Name, Studio, Category, Price, File type and File size. Example in the request is a layout example, not hardcoded data. Current public API already supplies title, creator, category, extension and bytes when available. Format file types safely and label unknown information “Not available” (or omit consistently); do not infer a price or say missing data is free.
- Make a known studio name a link to a studio-filtered catalog with pagination, so it can show all matching public items rather than only the first 24 free-text matches. Proposed Worker `creator` equality filter, correctly escaped and parameterized; preserve query/category/page state. Names are not stable studio IDs and can collide, vary in spelling/case, or be missing, so exact-name results are best effort; do not claim studio identities are verified.
- Price: D1 and the public `/addons` API do not currently store Minecoins or USD. The revision-66 local bot snapshot extracts some price metadata in upload-session processing, but the `files` row and website sync shown locally do not persist or send it; live revision 68 is not verified. The old extractor can estimate dollars from coins, so do not treat all available dollar strings as authoritative. Investigate a reliable permitted source and source/currency/time semantics first. Plan a separately approved additive D1/schema and sync/backfill design if accurate data can be obtained automatically, without manually entering packs or overwriting the live bot; otherwise display “Not available.” Never apply pending Telegram migrations. Present Marketplace price as a reference, not the price of the bot-delivered file; prices can differ by region/time.
- Studio icon: no trusted studio icon field or stable studio ID is currently in the public metadata. Research a permitted official source, provenance and CORS; add an actual icon only where verified, with an accessible fallback. Do not use the pack thumbnail as a studio logo, invent a logo, rely on untrusted arbitrary proxy, or promise every studio has one.

## 4. First 3–4 cards and performance

- Measure current cold and warm page load separately, including real-host HTML/challenge, Worker response, first card/image paint and 3–4 cards, on mobile and desktop. Show the shell immediately and honest loading placeholders; never fabricate listings.
- Safe first step: start the existing catalog metadata request as early as possible in the page, reuse the same in-flight response once, and render the first four valid cards immediately on receipt; schedule remaining card DOM work in small chunks without blocking input. Request the initially visible thumbnail(s) eagerly at high priority and lazy-load the rest. This does not make the data arrive before the network returns the current full 24-item JSON, nor can it guarantee an instantaneous load. Retain accessible loading, empty/error/retry and correct page counts.
- If measurement shows response payload/network is still the bottleneck, separately evaluate a compatible bounded first-4 plus remainder API (cursor-based, validated and deterministic). A second request can cost more and introduce duplicates, omissions or reordered records if updates occur; design deduplication, partial-load/retry behavior and consistency limits, test pagination/filter combinations, and compare real timings before rollout. Requires an approved Worker change/deployment; retain the old endpoint contract and no-store. Do not silently introduce persistent/session metadata caching, a service worker, stale data or change deletion semantics.
- Preserve browser history/return behavior and `no-store`; no promises of offline download, zero latency, complete catalog import or immediate deletion reconciliation.

## Research note: user-supplied Marketplace API documentation

- `https://github.com/MC-Marketplace-Bot/Minecraft.net-Marketplace-view-API-documentation` was inspected at commit `6a9ef2b9604c8507c7fa852e73da5e6d955b0b08`. It is archived and its README explicitly says the documented Minecraft.net endpoints are outdated after a Mojang service migration. It describes historical product details, autosuggest, creator search and sales endpoints, but does not document current response payloads or verify studio icons, prices or upload timestamps. Independent fetch attempts for an old product-details endpoint and creator search failed without a usable HTTP status; these attempts do not prove the current behavior of every endpoint. Treat it as historical context, not a production dependency.
- The local rev-66 Marketplace module already contains the old endpoint as a fallback and comments that the endpoints returned 404 in earlier observations. The live rev-68 bot and its current behavior are not verified; do not replace or deploy it.
- Microsoft’s generic PlayFab Economy GetItems documentation lists possible item properties such as creation date, images and price options, but requires an `X-EntityToken`: `https://learn.microsoft.com/en-us/rest/api/playfab/economy/catalog/get-items?view=playfab-rest`. This is generic platform documentation, not evidence that Minecraft exposes those properties or permits this site to use that API. No credential, rate, price, studio-icon or copyright assumption is justified without further checks. Research only; no changes/deployment to the website, Worker or bot.
