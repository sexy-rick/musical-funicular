## Deep research: opening in Minecraft

### Evidence and existing Alium behavior

- Microsoft's Bedrock creator guide documents Android import by opening the downloaded world or add-on file; Minecraft itself displays import success. `.mcworld` is a world archive; `.mcpack` is a resource/behavior/skin pack; `.mcaddon` is an add-on bundle. A valid import may still need activation in the relevant world. https://learn.microsoft.com/en-us/minecraft/creator/documents/gettingstarted?view=minecraft-bedrock-stable and https://learn.microsoft.com/en-us/minecraft/creator/documents/minecraftfileextensions?view=minecraft-bedrock-stable. Templates `.mctemplate` merit testing; Microsoft's template documentation describes their use, not a blanket guarantee for every Android edition: https://learn.microsoft.com/en-us/minecraft/creator/documents/createaworldtemplate?view=minecraft-bedrock-stable.
- Current `android-app/android-template/MainActivity.kt`'s `open` uses generic `ACTION_VIEW` with the saved `content://` URI, provider MIME or `application/octet-stream`, and read grant; it does not set the Minecraft package. Android can therefore resolve to an archive app. The screenshot of a completed `.mcworld` shows a history entry but does not establish the observed app chooser/default behavior or import success.
- Android documents that `Intent.setPackage` constrains resolution to a package, and `FLAG_GRANT_READ_URI_PERMISSION` grants access to the content URI in data/ClipData. The official Play listing identifies the main game as `com.mojang.minecraftpe`: https://developer.android.com/reference/android/content/Intent and https://play.google.com/store/apps/details?id=com.mojang.minecraftpe&hl=en_ZA. This establishes a targeting mechanism, **not** which particular intent/MIME the user's Minecraft build will accept.
- Android PackageManager visibility filters installed-app queries on Android 11+, but explicit activity starts do not inherently require broad visibility. Declare a narrowly scoped `<queries>` entry if querying the official Minecraft package, never `QUERY_ALL_PACKAGES`, and handle ActivityNotFoundException and SecurityException: https://developer.android.com/training/package-visibility/use-cases and https://developer.android.com/training/basics/intents/package-visibility.
- A third-party MIT repository, `hoangvan200/minecraft-resource-importer` at `d43a466205da6d295af300b987563dd119fa1ed9`, describes ACTION_VIEW, original extension, FileProvider, URI read permission and an Android chooser, but explicitly says native behavior requires device testing; it is not proof that a given direct intent imports on the user's Minecraft. Another third-party source (`samuelebruzzese12-stack/minecraft-mod-installer`, `9bb8ad483ab5e3f38b84c487e9881ee14043ff57`) uses `setDataAndType` + ClipData + grant, tries an explicit component and package, and its own CI contains a **fake Minecraft app**. Source observations are not validation against real Minecraft. Neither project is being copied.
- A 2020 Stack Overflow answer proposes `minecraft://?import=<raw path>`; no verified current Android/Minecraft support or secure modern `content://` behavior was established. Do not rely on old raw paths or claim it is an official import API. https://stackoverflow.com/questions/64483146/how-to-send-android-intent-to-minecraftpe-with-mod-file-mcpack

### Implementation design

1. Downloads tap checks **saved and complete** record, file readability and extension (`.mcpack`, `.mcworld`, `.mcaddon`; `.mctemplate` only after specific device validation). Keep a distinct case for unsupported ZIP/RAR/7z/APK, unknown or malformed file: no pretending it is a Minecraft pack, no automatically installing APKs, and no broad archive extraction. The download itself remains available.
2. For a supported file, take app-owned MediaStore URI or persisted SAF URI with the original display name/extension. Construct `ACTION_VIEW` with data and type in the **same** `setDataAndType` call, pass URI via ClipData, temporary read grant, restrict target to `com.mojang.minecraftpe`, and call `startActivity` on the user's tap. Verify which MIME/URI combination the actual installed game accepts; `application/octet-stream` is a **candidate**, not a known universal Minecraft contract. Do not silently route to other apps. No direct access to Minecraft's Android/data or root, no all-files permission, no use of browser or ZArchiver.
3. Minecraft may care about display name or a `content://` URI with an extension path. If the direct MediaStore/SAF URI is rejected, consider a restricted FileProvider cache copy with sanitized original filename and extension; stream off the UI thread, handle space and cancellation, maintain it long enough for Minecraft to read it, and clean it up later without deleting the user's saved download. Grant only read access, never expose the TDLib session or whole filesystem; do not rename/change original bytes.
4. Targeting explicit component/launcher or undocumented `minecraft://` is **not** presumed equivalent to import: launching a game's main screen can succeed while discarding the file. Only add an alternative if tested against real versions and it preserves URI permissions. Import must not use a generic chooser by default, even on failure.
5. Failure behavior: concise “Minecraft couldn't open this file.” or “Minecraft is not installed.” Offer **Retry**, an optional store link, and optional independently chosen generic Open with only if the user explicitly requests it; never send them to ZArchiver automatically. If different Minecraft versions/editions are installed, prioritize the official package and do not assume unofficial package names. Get the user's edition/version if direct import fails.
6. Android generally reports only whether the activity was launched, not Minecraft's in-game import result. Use “Opening in Minecraft…”; never show “Imported successfully” solely from `startActivity`. Minecraft may reject corrupted, unsupported, incompatible, protected or duplicate content. Pack activation may still be required; the source file is retained.

## One-tap bot download and pause design

- Flow: explicit Download tap → brief consent if needed → requesting → waiting for bot → validated target file(s) → downloading automatically → saving → downloaded. No second tap for normal identified file. A user can pause during waiting/downloading; mark paused before async callbacks, don't auto-start or save after cancel/logout, and resume deliberately. Offer progress and cancel, and release the active request automatically only once all intended files are handled.
- TDLib `downloadFile` starts/resumes requests and emits `updateFile`, while `cancelDownloadFile` stops one; these are real primitives. Whether partial bytes survive pause, process death, logout, or eviction with the pinned build must be tested before promising lossless resume. https://core.telegram.org/tdlib/docs/classtd_1_1td__api_1_1download_file.html and https://core.telegram.org/tdlib/docs/classtd_1_1td__api_1_1cancel_download_file.html. Show accurate state, never fake pause/progress.
- The owner trusts the bot to return the right item, but the checked-in old bot backup sends documents without a request ID; the app accepts messages after a given request, so a concurrent Telegram session, delayed answer or multiple documents can be confused. Need to inspect the live rev68 behavior and try message-reply metadata before declaring correlation. To guarantee fully automatic correct-file selection, prefer compatible per-request response markers and explicit end/error from a test bot; changing/deploying live bot requires separate approval and no database migration by default. Where the reply cannot be uniquely established, retain an exceptional compact file choice/failure state instead of silently attaching the wrong file; no long warnings. Never claim fully reliable one-tap until proved.
- Don't claim transfers persist through force stop, process death or reboot until a real TDLib/background-worker lifecycle is designed and tested.
