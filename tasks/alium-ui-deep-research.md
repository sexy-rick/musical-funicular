# Alium Android — UI research and implementation review

**Research date:** 27 November 2026. Based on checked-in Flutter UI, current bot/download code, the earlier Toolcoin screenshots and research, and website design decisions in `tasks/ui-research.md`, `tasks/expressive-website-plan.md` and `DESIGN.md`. Research is targeted, not a claim to have exhaustively read every external design resource. App changes are local only; not released or deployed.

## Goals and existing constraints

Users need to find an item, understand known attributes, start one Telegram transfer with their own account, see honest progress, open supported files in Minecraft, and manage saved files. Alium's independent identity stays: flower, `#874F9E` seed, `alium.amberlyst.com`, flat Material 3, no decorative AI glyphs, emojis, arrows, gradients or glow. Keep the current light/dark/system and accent preferences, support links, transfer controls, storage selection, Telegram login and user privacy. Help/consent should use short 4–6-word lines where practical. A layout that resembles a Toolcoin screenshot must not misrepresent data or copy source/assets.

## Evidence and implications

1. **Android adaptive design.** Android recommends layouts that respond to available window space, bounded dialogs/sheets on large screens, navigation rail for large widths where useful, and 48dp touch targets. See https://developer.android.com/docs/quality-guidelines/adaptive-app-quality/tier-2 and https://developer.android.com/guide/topics/ui/accessibility/apps. Decision: bound details, Downloads and Settings to a 760dp readable content width; use existing Material controls and wrapped action chips. Navigation rail and full window-size-class work remain future work; do not claim a tablet audit.
2. **Accessible text and interaction.** Flutter advises large text support, adequate contrast, labeled controls and testing with a screen reader, large scale factors and accessibility guideline API. See https://docs.flutter.dev/ui/accessibility and https://docs.flutter.dev/ui/accessibility/accessibility-testing. Decision: native labels/semantics, preserved text scaling, support non-color status, 48dp controls where Material defaults allow; add targeted widget tests. No claim of WCAG or TalkBack conformance without audit.
3. **Expressive hierarchy.** Website research used type hierarchy, strong primary actions, rounded containment and restrained interaction rather than every component competing for attention. Apply this to app sections: details image/title/action, a prominent active download, grouped settings, calm empty states. Keep flat solid semantic theme colors and existing reduced-motion-aware press effect. Avoid marketing tricks and invented stats.
4. **Honest progress.** Material distinguishes determinate from indeterminate progress; a progress bar should convey real status and have an accessible label. https://github.com/material-components/material-components-android/blob/master/docs/components/ProgressIndicator.md . The app knows TDLib file `downloaded` and `bytes` when provided. For known sizes show transferred/total; unknown size is indeterminate. Saving, paused, and waiting are distinct controller states; no invented overall percentage or ETA, automatic background persistence, transfer-speed guarantees or silently retrying claims.
5. **Search consistency.** The website's search blueprint distinguishes loading, empty results and error/retry; suggestions were real catalog results with stale response checks and no persistent caching. `FutureBuilder` previously displayed old results during a replacement future, which can look like matches for a different query. Local change shows a labeled loading state instead. Flutter's FutureBuilder ignores completions from an unsubscribed old future; old network requests are not aborted. Android autocomplete, request cancellation, latency profiling and search benchmarks are **not** implemented; current query debounce and real Worker API remain unchanged. Current `no-store` behavior is not replaced with persistent response caching.
6. **Images and long lists.** Flutter recommends lazy builders for large lists and avoiding expensive unnecessary rendering. https://docs.flutter.dev/perf/best-practices . Existing catalog grid already uses a lazy sliver and reserves a 16:9 image; fallback remains legible. Downloads currently constructs history rows eagerly: test real history sizes before deciding on a builder. No new image cache, gallery, false media, large downloaded assets, animation library or server is needed for this UI pass.
7. **Toolcoin/data.** The prior detailed research `tasks/alium-toolcoin-details-downloads-settings-plan.md` establishes that Toolcoin models gallery, video, ratings and price and performs authenticated catalog lookups; the current Alium Worker doesn't supply these fields. One third-party Trollcraft listing is only a proof of visible metadata, not a reuse license. Until access, currency semantics, license, freshness and multi-UUID live mapping are verified, do not fake a gallery, trailer, rating, price, or show an unresponsive button. Data-source integration and updater remain separate future work.
8. **Download/import limits.** Existing controller handles at most one request, with automatic TDLib file transfer, pause/cancel and a best-effort quiet period. Chat/message-order matching is heuristic, and direct Minecraft intent, actual delivery, resume retention, SAF folder persistence, background behavior and import success remain unverified on a device. UI must not imply guaranteed correlation or import; Telegram recovery appears contextually when a bot request fails/times out.

## Screen-by-screen audit and local changes

| Area | Before / concern | Local UI work | Remaining validation |
| --- | --- | --- | --- |
| Browse/search | Search's old results remained while new future loaded; hint could be insufficient label | Explicit search label and replacement loading state; existing filter, request action and pagination preserved | Keyboard, interrupted/rapid queries, real latency and all text scales |
| Details | Unstructured metadata, unavailable price text consumed space | Constrained layout, readable title/creator, direct Download/Share, rounded details group containing only real known fields | Real source for description/gallery/video/ratings/prices, if permitted; small/large device tests |
| Downloads | Status, controls and history visually mixed; unknown sizes could be confusing | Grouped active/empty/saved cards, truthful file-byte progress, pause/resume/cancel and per-file menu retained | Multi-file, bot gate, pause, saving, cancellation, history/open/share/delete and real phone |
| Settings | Controls mostly loose vertical list | Separate account, appearance, storage, support and about rounded groups; keep all preferences and links | Long text, SAF permission loss, dark/contrast and screen reader |
| Account | Unrequested profile audio and media dependency | Remove profile music UI, player code and `just_audio`; keep avatar, name, username, ID, bio and login | Actual login/logout and retained session on Android |
| Updates | No updater or public release feed | No misleading control | Separate approval and decisions per `tasks/alium-in-app-update-plan.md` |

## Verification plan and limits

- New widget tests cover basic Downloads empty/active states, settings rendering at narrow width, profile music removal with profile fields preserved, and website-style catalog action ordering and large-text fallback. Existing fake TDLib transfer tests remain. Syntax parsing and `git diff --check` are local checks only; Flutter SDK is not available locally. GitHub Actions run `46125602276` subsequently passed Flutter analysis, tests and signed release build on commit `109fef0`.
- Before shipping: Flutter analyzer/tests, 320/360/600+ width, system/light/dark and accent themes, 1x–2x+ text scaling, reduced motion, touch target/contrast guideline tests, keyboard navigation and TalkBack. Exercise long/missing metadata, loading/error/no results, search/filter reset, screen rotation and image failure. Measure rather than promise performance.
- On real Android: Telegram sign-in, one-tap multi-file transfer, bot gate and recovery, pause/cancel, stored history, permissions and storage, direct Minecraft package open and import confirmation, app restart, change theme and sign-out. Verify audio dependency is absent from generated release artifacts. No claim these checks have passed.
- Out of scope: changing the live bot/Worker/schema, public repo visibility/release, PlayFab credentials, updater, website or hosting deployment. Do not apply pending Telegram migrations.
