Status: implemented locally as v6; production upload and real-device checks pending. Date: 2026-11-27. Research: `tasks/pixelplayer-ui-research.md`.

## Goal and constraints

Improve the InfinityFree catalog with main channel and support links, functional icons instead of decorative symbols, faster return navigation, a custom sharing sheet, Auto/Light/Dark themes and restrained Material 3 Expressive-inspired motion. Stay within $0 and the current PHP → browser → public Worker/D1 → Telegram architecture. Preserve the no-gradient/no-glow/no-AI-style instruction, user's channel URLs, one large card per mobile CSS viewport and four cards per desktop row, UUID routes, existing old links, category/search/page state, access controls and versioned asset filenames. No new bot features, migrations, R2, login or paid services are implied.

## 2. Theme tokens and motion

- Add three understandable options: **Auto** (follows OS, including changes while open), **Light**, **Dark**. Map all surface/text/outline/action/focus/status/error colors to semantic CSS tokens, including static error pages, footer, native controls and share menu. Save preference when storage is available; degrade safely if disabled. Set theme as early as possible to reduce flashes and preserve working JS-disabled default. Set appropriate `color-scheme` and update theme-color where supported.
- Material 3 Expressive-inspired, not a cloned Android UI: solid surfaces, strong readable type, restrained expressive radii and clear selected states. Apply motion only to intentional interactions (button press, theme selector, opening/closing sheet) with lightweight CSS and a compatible easing fallback; no heavy animation framework without performance proof. Honor `prefers-reduced-motion`; no layout shift, infinite animation, scroll hijack or delay to use. Avoid motion-heavy OS imitation.
- Verify contrast for normal/large text and controls, focus, keyboard, screen-reader labels, forced-colors/high contrast, reduced motion, and themes on every route; do not assert full compliance without audit.

## 3. Return-to-catalog performance

- Reproduce separately: (a) browser Back, (b) explicit Back to collection, (c) reload/new tab. Record API request count, `pageshow.persisted`, page/filters/search/scroll and timings; inspect BFCache blockers. Preserve existing HTML revalidation and ensure no unload handler blocks BFCache. Prefer genuine history restoration when safe, while providing a normal catalog fallback for direct arrivals and retaining category/page/scroll.
- Define caching policy before code: Worker currently sends `Cache-Control: no-store`. If needed, separately approve a deliberate Worker public-metadata policy/TTL and test any deploy with all existing CORS/bindings/secrets preserved; don't store private data or misrepresent stale state. Prefer a bounded per-tab session cache for validated successful public catalog responses keyed by schema version, API, category, page and query, with modest TTL and bounded LRU; no error or auth payloads. On failure handle corrupt/quota-disabled storage and fall back to network. An initial candidate is 60 s fresh, up to 5 min stale with an explicit indicator/retry; confirm acceptable stale/deletion behavior before shipping. Use background revalidation only where policy allows, and avoid fetch loops; record measurable request reductions.
- No guarantee immediate deletion, complete backfill or offline downloads. Cache can't fix bot sync, D1 consistency or network restrictions. No service worker, persistent image cache, proxy or API schema changes unless later justified.

## 4. Custom sharing menu on card and detail

- One shared component with a proper modal/bottom-sheet: item title, link and labeled destinations **Telegram**, **WhatsApp**, **Discord**, **More**, **Copy link**. Support keyboard focus, Escape/backdrop dismissal, return focus to originating button, live status, large targets, both themes and reduced motion. No nested links/buttons. Sharing always uses canonical readable slug with the UUID and version once; `?i=1` is not copied, although the host can add it when a visitor opens it.
- Telegram official `t.me/share/url` and WhatsApp-supported link sharing can send URL/text, not guarantee a file. Discord must use a verified supported sharing route or clearly labeled native More/copy fallback; do not pretend to open an app-specific share target if unsupported. Preserve current direct Download links and Telegram fallback.
- User wants image attached by default in the native More sheet. Prepare a real thumbnail `File` only when the user opens the sheet (or by a bounded cache), after verifying image origin permission, type and size. On the final direct click use `navigator.canShare({files})` and `navigator.share` if supported, passing the image plus link/text as supported. Do not fetch on the final click and assume browser activation persists. Cancellation is not an error; if image access/CORS, format, browser, OS or share target prevents attachment, explicitly offer link-only sharing/copy and avoid suggesting an image was attached. Some targets may drop text or files; user chooses recipient. Test real Android Chrome and Firefox and record results. No arbitrary cross-origin proxy or scraping of a host security challenge.
- Official icons: source and use only permitted platform assets; vector preferred. Review Telegram/WhatsApp/Discord brand guidelines individually before including assets; no invented official logo or endorsement. Rich link preview is separate from file attachment and may fail on InfinityFree's bot check/client-rendered HTML.
